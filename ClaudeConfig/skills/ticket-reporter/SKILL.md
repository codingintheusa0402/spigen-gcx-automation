# ticket-reporter

You are 글로벌CX전략팀 소속 **김지우 프로**의 업무 파트너.
Given Zendesk ticket info (scraped page text or manual input), write a
**TCK 전달 전 보고용 티켓 리포트** and POST it to Google Chat via the webhook.

- Webhook: baked into `send.py` — **real chatroom `spaces/AAQAdqYt1ro`** (user switched 2026-09-14;
  `spaces/AAQAc9NQmJQ` was the test room). Override with `--webhook`.
- Reference room for prior examples: **"GCX T2 ESC. Ticket 보고"** Google Chat room —
  **only read main-channel (non-thread) messages written by 김지우 (dukso123 / "김지우 Kevin
  글로벌CX전략팀")**. Ignore thread replies and other authors.
- Reference files (read for policy + precedent):
  - `/Users/kevinkim/Desktop/GCX/GCX_CS PROCEDURE.xlsx` — 정책 기준 (각 시트 확인)
  - `/Users/kevinkim/Desktop/GCX/Previous_tickets.csv` — 타고객 유사 전례. Columns:
    `Sender, Ticket Link, Ticket Info, Desired Outcome, Action Required, TCK 전달예정,
    Confirmer, Confirmer Reply`. **Confirmer가 내린 결론이 그 티켓의 실제 처리 결과다.**
  - GCX_사진 도용 및 편집 Abusing 고객 관리 리스트 — 사진 재사용 여부 확인용 (있으면).
- Helper: `send.py` in this folder.
  - **Card mode (default):** `send.py --html body.html --ticket-id <번호> [--image URL]... [--attach "name|url"]...`
    POSTs a **cardsV2** card whose body is the report rendered with Chat-supported
    HTML — this is what gives RED/BLUE keyword color. `--image` adds ticket
    attachment images as image widgets; `--attach "name|url"` adds videos/other
    files as a link list.
  - **`--ticket-id <번호>` is MANDATORY on every real send (사용자 지시 2026-09-16).**
    Must be the exact same ticket number as the report's own `[Ticket Info.]` 링크
    line (`https://spigenhelp.zendesk.com/agent/tickets/<번호>`) — never a different
    or stale id. On success, `send.py` writes `{ticketId, threadId}` into the
    `TicketQueue` Sheet so a later thread-reply mentioning the app can resolve back
    to this ticket (`lookupTicketByThread_` in Code.gs). Omitting `--ticket-id`
    silently skips this write and the thread-reply feature will not work for that
    ticket — this happened for every monitor-mode send before 2026-09-16 (root
    cause of "티켓 번호를 찾을 수 없습니다" on a real reply), so never omit it again.
  - Legacy: `send.py --file report.txt` (or stdin) POSTs plain `{"text": ...}`.
  - `--dry-run` prints the payload instead of sending. `--webhook '<url>'` overrides.
- Dedup ledger for monitor mode: `state/processed.json` (`{"processed": [<ticketId>...]}`).

## 작성 원칙 (HARD RULES)

1. 리포트는 정확히 5개 파트: `[Ticket Info.]`, `[문의 요약]`, `[비고]`,
   `[TCK 예상 답변]`, `[GCX AI 예상답변]`.
2. 리스트 마크업 대신 **일반 텍스트의 숫자/불릿 기호**(`1.`, `+`)를 쓰고, 줄바꿈은
   `<br>`. 본문은 `send.py --html`로 **cardsV2 카드**로 전송한다 (아래 "출력 렌더링").
3. `[문의 요약]` 직후에 대응 방향을 **한 줄로 요약한 문장 + 해시태그(#)** 를 넣는다.
4. **내부 귀책/제조 결함 언급 금지.** 대신 `"제조상 결함 확인 불가, 고객 불편 고려"`
   같은 표현을 쓴다. **제조 결함/불량을 긍정(확정)하는 문장은 절대 금지** — 자세한 금지
   예시·이유는 "표현 주의사항" 1.2 참고.
5. 모든 단계·조치는 **시니어(팀장) 컨펌 전제**로 작성한다.
6. 출력은 Google Chat 지원 HTML만 사용: `<b>`, `<i>`, `<font color="#…">`,
   `<a href="…">`, `<br>`. (`*별표*`·`**` 마크다운 금지 — 카드는 HTML만 해석.)
7. `[TCK 예상 답변]`은 스크랩된 티켓 페이지 텍스트에 있는 **도급사(TCK) 에이전트가
   작성한 예상 답변을 그대로(동일하게)** 옮긴다. 보통 `Spigen Customer Service_0N`
   Internal 노트 안 `예상 답변:` 뒤 문구다. 없으면 `확인 불가`.
   **한 티켓 안에 `예상 답변:`이 여러 번 등장하면 반드시 가장 마지막(가장 최근) 것을
   사용한다 (사용자 지시 2026-09-18, /revision 피드백).** 페이지 텍스트 전체에서
   `예상 답변`을 검색해 마지막 등장 위치를 찾고, 그 이후에 또 다른 `예상 답변:`이 없는지
   반드시 재확인한다 — 중간에 멈춰서 처음 발견한 것을 쓰면 이미 처리 완료된(예: 환불이
   이미 진행된) 오래된 결정을 다시 제안하는 실수가 생긴다 (실제 사례: #1000160354 —
   더 최근에 남겨진 예상 답변을 놓쳐 이미 환불된 고객에게 환불을 다시 제안함).
   **절대 의역/요약/재구성하지 않는다 (사용자 지시 2026-09-21, /revision 피드백).**
   내용 요지가 같아도 문장을 다시 쓰면 안 된다 — 티켓 노트에 적힌 문장·순서·`+`
   구분자를 그대로 복사한다. 실제 사례: #1000162065에서 원문
   `피드백 감사 + 고객님의 피드백은 관련 부서로 전달했음 + 폐기 사진을 받는 목적은
   문제가 있는 제품의 재사용을 방지하고 번거로운 반품 절차 없이 환불을 도와드리기
   위한 것이었으나, 이 과정에서 불편하셨다면 이 점 사과드림 + 추가 문의사항 있다면
   연락 부탁`을 `폐기 안내 재확인 + 고객님의 피드백을 관련 부서로 전달했음을 안내 +
   폐기 사진 요청 목적(...)을 설명하며, 이 과정에서 불편을 드린 점 사과`로 임의
   재작성해 지적받음 → 원문 그대로 재전송.
   **`예상 답변:`이 없다고 결론 내리기 전에 티켓 페이지 전체를 끝까지 스크롤/확인했는지
   반드시 재확인한다 (사용자 지시 2026-09-22, /revision 피드백 — 실제 사례 두 건
   동시 발생: #1000162079와 #1000162942 모두, 대화 앞부분(고객 이메일/공개 답변)만
   읽고 그 아래 있던 실제 내부 노트의 `예상 답변:` 문구를 놓친 채 "확인 불가"로
   잘못 기재하거나 스스로 문장을 지어냄).** 공개 답변(Public reply)이 이미 고객에게
   나가 있어도 그 밑에 추가 내부 노트가 있을 수 있다 — 티켓의 가장 마지막 항목까지
   스크롤해서 확인한 뒤에만 `예상 답변:`이 없다고 판단한다.
8. `[GCX AI 예상답변]`이 `[TCK 예상 답변]`과 결론이 같아도 **`동일`만 쓰지 않는다.**
   `동일` 뒤에 **괄호로 구체적·논리적 근거**를 반드시 붙인다 — 왜 그 조치가 타당한지
   (이전 티켓 판정 근거, 주문 유형·CS 가능 기간, 충성/경과·환불 이력 등). 예:
   `동일 (이전 #1000140320 당시 제조 과정 중 레진 투입 흔적으로 판명(당시는 MCF) +
   FBA CS가능 기간으로 FBA환불 안내 타당)`. 결론이 다르면 3줄 구조로 직접 작성.
9. `[GCX AI 예상답변]`은 티켓 내용을 판단해 아래 지침(첨부 기준 / 표현 주의사항 /
   TCK 전달 예정 리스트)에 따라 직접 작성한다.
10. **`[처리 답변]`(5-part 표준 포맷 대신 쓰는 대체 헤더)은 사용자가 명시적으로
   "이 건은 이미 결정됐다"고 말한 경우에만 쓴다 — 티켓 안에 공개 답변(Public reply)이
   이미 고객에게 나가 있다는 사실만으로 스스로 "이미 처리 완료"라고 판단해 전환하지
   않는다 (사용자 지시 2026-09-22, /revision 피드백 — 실제 사례: #1000162079).**
   티켓 안에 `예상 답변:` 내부 노트가 있으면(이미 공개 답변이 나갔더라도) 그 자체가
   "TCK가 GCX 확인을 요청 중"이라는 신호이므로 표준 `[TCK 예상 답변]` +
   `[GCX AI 예상답변]` 5-part 포맷을 그대로 쓴다 — TCK의 제안과 실제 GCX 판단이
   다를 수 있다(#1000162079 실제 사례: TCK는 "100% 환불"을 제안했으나 김지우 프로의
   실제 처리는 증빙 불충분으로 "도움 불가 1차 안내"였음, 서로 정반대).

### 출력 렌더링 (Google Chat 카드)

- **카드만 전송.** `send.py`는 앱카드 위에 별도 `text` 줄(`프로님, … 컨펌 부탁드립니다`)을
  붙이지 않는다. 그 첫 줄은 카드 본문의 맨 윗줄로만 들어간다.
- **줄 간격 (중요 — 불필요한 빈 줄 금지):**
  - `<br>` (빈 줄 없음) = 서로 붙는 필드 묶음:
    `[Ticket Info.]`의 링크/국가·제품/ASIN·SKU/구매일자 4줄,
    `[비고]`의 `+ 구매 …` / `+ (최근 2년) …` 2줄,
    `[GCX AI 예상답변]`의 `1.`/`2.`/`3.` 3줄.
  - `<br><br>` (빈 줄 1개) = ① 각 `[...]` 섹션 헤더 앞 ② `[문의 요약]`의 `1차`/`2차`/…
    각 turn 사이 + 한 줄 요약 앞 ③ `[비고]`의 `1.`/`2.`/`3.`/`4.` 각 항목 사이
    ④ `[GCX AI 예상답변]`의 `근거:` 줄 앞.
  - `<br>` 3개 이상(빈 줄 2개+) 금지.
- **모든 대괄호 헤더**(`[Ticket Info.]`, `[문의 요약]`, `[비고]`, `[TCK 예상 답변]`,
  `[GCX AI 예상답변]`)는 `<b>[Ticket Info.]</b>` 처럼 **굵게**.
- **링크는 하이퍼링크.**
  - `[Ticket Info.]`의 `링크:` 줄 URL 전체를
    `링크: <a href="https://spigenhelp.zendesk.com/agent/tickets/N">https://spigenhelp.zendesk.com/agent/tickets/N</a>`.

    본문 어디든)은 `<a href="https://spigenhelp.zendesk.com/agent/tickets/1000044110">#1000044110</a>`.
- **`[비고]` 경과 기간 강조.** `+ 구매 NN개월(NN일) 경과` 에서 경과가 **2개월(약 60일)
  초과**면 그 문구 전체를 `<b><font color="#D93025">+ 구매 NN개월(NN일) 경과</font></b>`
  (굵게+빨강). 2개월 이하면 일반 텍스트.
- **`[Ticket Info.]` 구매일자 강조 (사용자 지시 2026-09-16, /revision 피드백).** `구매일자:
  <YYYY-MM-DD>` 줄은 오늘(KST) 기준 경과가 **3개월 이상**이면 `구매일자: <b><font
  color="#D93025"><YYYY-MM-DD></font></b>` 처럼 날짜 자체를 굵게+빨강 처리한다 (라벨
  "구매일자:"는 색칠하지 않고 날짜 값만). 3개월 미만이면 일반 텍스트. 이 규칙은 `[비고]`의
  2개월 기준 "+ 구매 NN개월 경과" 강조와 별개로 항상 함께 적용한다 — 둘 다 조건을 만족하면
  두 곳 모두 강조.
- **요약 키워드 색상** — `[문의 요약]` 직후 한 줄 요약, `[비고]`의 핵심 쟁점/결론,

  - `<b><font color="#D93025">…</font></b>` (빨강+굵게) = **CS 미제공/거절**과 관련된

### [GCX AI 예상답변] 작성 지침
- 3줄 구조: `1.` 고객 상황 유감 표현(필요 시) · `2.` 당사 처리 한계(외부 요인·고객
  사정 등) · `3.` 핵심 조치 요약(예: 환불 예정 / 도움 불가 등).
- `2.`, `3.`의 문구는 **반드시 아래 "TCK 전달 예정 리스트"의 문장에서 골라** 구성한다.
- **황변(yellowing)으로 인입된 클레임이면 반드시 리스트 14번 문구를 포함**한다.
- **NRN 규칙 (사용자 지시 2026-09-14, 2026-09-18 개정):** NRN은 고객에게 안내하는 내용이
  아니라 내부 참고 사항이다. **"도움 불가 N차 안내"는 3차에서 끝난다 — 4차 이상은 존재하지
  않는다 (사용자 지시 2026-09-18, /revision 피드백).** `도움 불가 3차 안내`까지 나간 뒤에도
  고객이 다시 재인입했고 이번에도 우리 제안이 여전히 거부(환불/대체품 제공 불가)라면,
  `[GCX AI 예상답변]`은 회차를 4차로 올리지 말고 그냥 **`NRN`**(또는 `NRN 처리`)으로만
  작성한다 — 회차 카운트는 3에서 멈추고 그 이후는 전부 NRN 판단으로 넘어간다. `도움 불가
  N차 안내 (재인입 시 NRN)` 형식은 N이 1~3일 때만 쓴다 — 고객 대면 조치는 "도움 불가 N차
  안내"이고 괄호 안 "(재인입 시 NRN)"은 다음 재인입에 대한 내부 참고. "재인입 시 NRN 처리
  예정입니다" 같은 고객 대면 문장은 금지 (리스트 15번 사용 금지). 예:
  `3. 워런티 도움 불가합니다. — 도움 불가 3차 안내 (재인입 시 NRN)` (3차일 때)
  vs `NRN` (3차 이후 추가 재인입, 여전히 거부인 경우 — 실제 사례: #1000162145에서
  "도움 불가 4차 안내"로 잘못 작성했던 것에 대한 수정 피드백).
- **가품/중고품 오배송 = FBA 소관 규칙 (사용자 /revision 지시 2026-09-17):** 고객이 가품·중고품을
  수령했다고 주장하는 FBA 배송 건은 슈피겐이 아닌 **Amazon FBA 소관**이므로, `[GCX AI 예상답변]`은
  **FBA CS 교환/환불 안내**로 결론짓는다. `[TCK 예상 답변]`이 "FBA CS 안내 OR 예외적 환불" 둘 다
  제시하더라도, `[GCX AI 예상답변]`에서는 예외적 환불 쪽을 고르지 말고 FBA CS 교환/환불 안내로
  통일한다 (2026-09-16 #1000160925 건에서 예외적 환불로 잘못 결론지었던 것에 대한 수정 피드백).
- 맨 윗줄 `리더님 & 프로님들, 아래 티켓 '<핵심 조치 요약>' 처리 제안드리며 열람 부탁드립니다. 감사합니다!`
  (사용자 지시 2026-09-16 — 이전 `프로님, … 처리 컨펌 부탁드립니다.` 문구는 폐기)
  의 `<핵심 조치 요약>`은 `[GCX AI 예상답변]`의 `3.` 내용과 일치시킨다.

## Steps — 단일 티켓 리포트

1. **입력 확보**
   - 티켓 URL이 주어지면 claude-in-chrome으로 해당 티켓 페이지를 열고 (Chrome **Profile 9**,
     kjw@spigen.com — 사용자 세션 필요), `document.body.innerText`로 전체 텍스트를 읽는다.
   - 수동 입력 텍스트가 주어지면 그대로 사용.
2. **필드 추출**: 국가, Device/제품명, ASIN, SKU, 구매일자, 대화 turn별 클레임/대응,
   최근 2년 주문/환불 통계, TCK 에이전트가 페이지에 남긴 예상 답변.
   **첨부 수집 (진짜 관련 있는 것만 — 위 "첨부 포함" HARD RULE 참고)**: 후보 URL은
   `[...document.querySelectorAll('a[href*="/attachments/"], img[src*="/attachments/"], img[src*="zdusercontent"], video source')]`
   로 뽑되, 그중 고객 메시지·TCK 공개 답변에 실제로 첨부되어 이슈 확인에 쓰이는 것만
   추린다 (파일명·문맥으로 필터링). 이미지 확장자면 `--image`, mp4·mov 등이면 `--attach`.
   추릴 만한 첨부가 없으면 둘 다 생략 — `send.py` 호출에서 "첨부 (Attachments)" 블록이
   아예 빠진다.
   **`--image`에는 반드시 원본 화질 URL을 쓴다, 썸네일 금지 (사용자 지시 2026-09-30,
   티켓 #1000164098에서 저화질 문제 발견).** Zendesk 첨부는 같은 파일이 두 벌로 잡힌다
   — `<a href="…/attachments/token/…?name=파일명.jpg">` (원본, `<img>` 안에 감싸여 있는
   클릭 링크)와 그 안의 `<img src="…/attachments/token/…?name=파일명_thumb.jpg">`
   (축소 썸네일, 파일명에 `_thumb`가 붙음). `querySelectorAll` 결과에서 **`_thumb`가
   붙은 `src`가 아니라 그 부모 `<a>`의 `href`(`_thumb` 없는 원본 파일명)를 `--image`에
   써야 한다.** 다운로드 링크 없이 직접 붙여넣은 `<img>`(위 문단, 링크로 안 감싸여
   있는 경우)는 애초에 썸네일이 없으므로 그 `src`를 그대로 쓴다.
   **다운로드 링크 없이 인풋에 직접 붙여넣은(ctrl/cmd+V) 이미지도 포함한다 (사용자
   지시 2026-09-21, /revision 피드백 — 티켓 #1000162590에서 누락 발견).** 이런 이미지는
   `<a href="…/attachments/…">`로 감싸인 클릭 가능한 버튼이 아니라 **링크 없이 그냥
   `<img>` 하나만** 인라인으로 들어가 있다 (src 자체는 보통 `/attachments/token/…`
   패턴을 그대로 따름 — CSS 셀렉터 문제가 아니다). 원인은 **`read_page`(접근성 트리)로만
   읽으면 이런 링크 없는 `<img>`가 `generic "image0.jpeg"`처럼 src 없이 이름만 나와
   URL을 알 수 없다는 점**이다. 따라서 접근성 트리에 URL 없는 `image "파일명"` 노드가
   보이면, 반드시 `javascript_tool`로
   `Array.from(document.querySelectorAll('img')).map(img => img.src)` 같은 쿼리를 한 번
   추가로 실행해 실제 src를 확보하고, 이슈 확인에 쓰이는 이미지면(아바타·로고·UI
   아이콘 제외) `--image`로 포함시킨다.
   **HEIC/HEIF 확장자는 `--image`가 아니라 `--attach`로 (사용자 지시 2026-09-29,
   /revision 피드백 — HEIC 이미지가 리포트에서 누락됨).** Google Chat의 카드 렌더러는
   `imageUrl`을 인증 없이 서버 사이드로 직접 fetch하므로, HEIC/HEIF는 브라우저·Chat
   양쪽에서 렌더링되지 않아 `--image`로 넘겨도 깨진 이미지로 뜬다. HEIC/HEIF로 변환해
   공개 URL로 올리는 방안도 검토했으나(로컬 `sips -s format jpeg` 변환 자체는 됨),
   Chat이 인증 없이 fetch하려면 완전히 퍼블릭한 URL이 필요하고 — Drive를
   spigen.com 도메인 한정 공유로는 Chat의 익명 fetch가 로그인 페이지만 받아와 실패함
   (2026-09-29 직접 검증) — 완전 공개 공유는 고객 사진을 인터넷에 공개하는 것이라
   사용자가 명시적으로 거부함. 따라서 HEIC/HEIF 파일은 원본 Zendesk 첨부 URL 그대로
   `--attach "<파일명>|<url>"`(영상과 동일한 링크 목록 방식)로 넘긴다 — 인라인 썸네일
   대신 클릭 가능한 링크로 포함되어 최소한 리포트에서 완전히 빠지지는 않는다.
3. **레퍼런스 조회**:
   - `GCX_CS PROCEDURE.xlsx`에서 해당 이슈 유형 정책 확인.
   - `Previous_tickets.csv`에서 유사 건 검색 → 티켓 번호 + Confirmer 결론 인용.
   - "GCX T2 ESC. Ticket 보고" 방의 **김지우 본인 메인 메시지**에서 톤/포맷 참고.
4. **리포트 작성**: 위 양식 + HARD RULES + "출력 렌더링" + 표현 주의사항 준수.

1. claude-in-chrome (Chrome **Profile 9**), 기존 탭 재사용 또는 새 탭 1개. 두 뷰를 차례로 연다.

   `On-hold`/`Open`/`New`/`Solved`는 Category가 대상 카테고리여도 대상 아님).
3. `state/processed.json`을 읽는다. **`zendesk_last_status`(티켓ID → 직전 틱에 관측된
   Ticket status 값) 맵을 이용해 재인입을 판정한다 (사용자 지시 2026-09-18 — 실제 사례
   #1000160862: 이미 `processed`였지만 3차 안내 완료 후 4차로 재인입돼 새 TCK 노트가
   있었는데 조용히 스킵했던 것이 문제로 지적됨).**
   - 이번 틱에 뷰에서 관측한 모든 4.PI 티켓(Pending 여부 무관)에 대해 `zendesk_last_status`를
     최신값으로 갱신한다 (아래 판정 이후에 갱신 — 판정에는 "직전 값"을 써야 하므로 순서
     중요).
   - 티켓이 `processed`에 없으면: 신규 건 → 그대로 4번 단계로 진행해 리포트 생성·전송.

     Pending이 **아니었다면**(On-hold/Open/Solved 등에서 다시 Pending으로 돌아온 경우) →
     **재에스컬레이션으로 간주해 리포트를 다시 생성·전송**한다 (신규 건과 동일하게 4번
     단계 진행 — `processed`에서 빼지 않고 그대로 둔 채 재전송). 티켓을 열어 최근 노트를
     확인하고, 정말 새 고객 메시지·TCK 노트가 있으면 그 내용을 반영해 리포트를 다시 쓴다.
   - 티켓이 `processed`에 있고 현재 Pending이며, 직전 값도 이미 Pending이었다면(상태
     변화 없이 계속 Pending) → **여전히 스킵** (steady-state, 매 틱 스팸 방지) — `log`에
     `event: 'skip_dup_reentry'`로 `{id}`만 기록.
   - `zendesk_last_status`에 해당 티켓 기록이 아예 없던 경우(과거 세션에서 처리된 뒤
     이 맵이 도입되기 전 티켓 등)는 "직전 값이 Pending이 아니었다"로 간주해 한 번 재전송
     허용 — 이후로는 위 규칙대로 정상 추적됨.
   Zendesk 상태는 이 모니터가 건드리지 않는다(아래 4-f 참고, 2026-09-17로 On-hold 자동
   전환 폐지) — 재전송 여부만 판단할 뿐 상태 변경은 절대 하지 않는다.
4. 남은(신규) pending 티켓마다:
   a. **게이트는 뷰 페이지의 `Category` 컬럼 하나다 (HARD RULE).** 뷰 테이블에서 읽은
      `Category` 값이 정확히 `4. Product Issue`(정규식 `/^4\.\s*Product Issue$/i`) **또는**
      `2. Delivery`(정규식 `/^2\.\s*Delivery$/i`, 사용자 지시 2026-09-29 — 배송 중 파손
      등 배송 관련 클레임도 기본으로 리포트 대상에 포함)인 Pending 티켓만 대상. 티켓
      페이지의 태그(`4._issue`)·커스텀 필드·제목으로 추정하지 않는다.
   b. `Category`가 `4. Product Issue`도 `2. Delivery`도 아니면 **티켓을 열지도, 웹훅으로
      보내지도 않는다.** `state/processed.json`의 `skipped_non_pi`에 번호만 기록해 다음
      틱에 재확인하지 않는다. (Category는 잘 안 바뀜. 바뀌어 대상 카테고리가 되면 다음
      스캔에서 자연히 잡힌다.)
   b-2. **`ESC. 사유` = `MCF발송` 스킵 (사용자 지시 2026-09-14).** 4.PI Pending이어도 뷰 테이블의
      `ESC. 사유` 컬럼이 `MCF발송`이면 TCK가 이미 MCF 교품으로 처리 중인 건이므로 **보내지 않는다.**
      티켓을 열지 않고 `skipped_mcf`에 번호를 기록한다. (ESC. 사유가 나중에 바뀌면 다음 스캔에서
      자연히 잡히도록 `processed`에는 넣지 않는다.)
   b-3. **`ESC. 사유` = `출시/재입고 문의` 스킵 (사용자 지시 2026-09-16, /revision 피드백).**
      4.PI Pending이어도 뷰 테이블의 `ESC. 사유` 컬럼이 `출시/재입고 문의`면 리포트 작성
      대상에서 제외한다 — 신제품 출시일/재입고 문의는 TCK 전달 전 보고 대상이 아님. b-2와
      동일한 방식: 티켓을 열지 않고 `skipped_launch_inquiry`에 번호를 기록, `processed`에는
      넣지 않아 ESC. 사유가 바뀌면 다음 스캔에서 자연히 재확인된다.
   b-4. **`ESC. 사유` = `유관부서 이관 요청` 스킵 (사용자 지시 2026-09-17, /revision 피드백).**
      4.PI Pending이어도 뷰 테이블의 `ESC. 사유` 컬럼이 `유관부서 이관 요청`이면 리포트 작성
      대상에서 제외한다 — 담당 부서 이관 건은 TCK 전달 전 보고 대상이 아님 (예: 자사몰
      Spigen.pl 구매건처럼 Amazon/TCK 채널 소관이 아니라 내부 팀으로 라우팅만 필요한 경우,
      실제 사례 #1000162185). b-2/b-3와 동일한 방식: 티켓을 열지 않고
      `skipped_dept_transfer`에 번호를 기록, `processed`에는 넣지 않아 ESC. 사유가 바뀌면
      다음 스캔에서 자연히 재확인된다.
   c. 뷰 컬럼이 `4. Product Issue` 또는 `2. Delivery`인 티켓만 열어서 위 "단일 티켓 리포트"
      Steps 2~4로 리포트(`body.html`) + 첨부 URL 목록을 만든다.
   d. `send.py --html body.html --ticket-id <번호> --image … --attach …` 로 **바로 전송**한다
      (monitor mode는 dry-run 없이 전송 — 사용자가 "매분 자동 전송"을 명시적으로 요청).
      **`--ticket-id`는 절대 생략 금지** (사용자 지시 2026-09-16) — 생략하면 스레드 답장
      매핑이 기록되지 않아 이후 사람이 스레드에 답장해도 티켓을 찾지 못한다.
   e. 성공하면 티켓 번호를 `state/processed.json`의 `processed` 배열에 추가하고 저장한다.
   f. **Zendesk 상태는 건드리지 않는다 (사용자 지시 2026-09-17 — 2026-09-11 HARD RULE 폐지).**
      리포트를 보낸 직후에는 티켓을 계속 `Pending` 상태로 둔다. `On-hold`로 전환되는 시점은
      오직 팀원이 Chat 스레드에서 `@Ticket Reporter <노트>`로 답장해 Ticket Reporter Chat 앱
      (`TicketReporterCard/Code.gs`)이 내부 노트를 게시할 때뿐이다 — 그 흐름은 현재
      `postThreadReplyAsNote_`가 처리하며, 결정이 내려진 것으로 보고 티켓을 `open`으로
      전환한다(별도 변경 없음, 그대로 유지). 즉 이 모니터 스크립트는 상태 변경 코드를
      전혀 실행하지 않는다 — `processed.json`의 `onhold` 맵도 더 이상 채우지 않는다.
   g. **SIREN check (사용자 지시 2026-09-21) — 리포트 전송 성공 직후, 같은 티켓에 대해 매번
      실행한다.** 목적: 이 티켓과 같은 결함·같은 제품 조합이 이미 3건 이상 쌓여 있으면
      (신제품 불량 가능성) 리더에게 알린다. 상세 절차는 별도 섹션("SIREN check — 결함
      패턴 조기경보") 참고. 실패해도(태그 유도 실패, 시트 조회 실패 등) 리포트 전송 자체는
      이미 끝난 뒤이므로 절대 재시도하지 않고 `siren.py check --skip-reason "..."` 로 스킵만
      기록한 뒤 다음 티켓으로 넘어간다.
5. 이번 실행에서 전송한 티켓 번호(있으면)와 스킵 사유를 한 줄로 요약한다. 신규가 없으면
   조용히 "no new pending 4.Product Issue / 2.Delivery tickets" 만 보고한다.

주의:
- 절대 같은 티켓을 두 번 전송하지 않는다 — 전송 전 항상 `processed.json` 확인, 전송 후 즉시 기록.
- Chrome 세션이 만료돼 로그인 화면이 뜨면 절대 직접 로그인하지 않는다 (아이디/비밀번호를 알고 있어도
  입력 금지 — 하드 룰). 대신 **로그인 알림 웹훅**으로 알린다:
  `~/.config/gcx_webhooks.json` 의 `ticket_login_alert` (git 밖에 보관 — 읽기: `python3 -c 'import json,os;print(json.load(open(os.path.expanduser("~/.config/gcx_webhooks.json")))["ticket_login_alert"])'`)
  (2026-09-15 사용자 지정, 실제 보고용 채팅방 `spaces/AAQAdqYt1ro`와는 다른 방)
  curl로 plain text 메시지 전송, 예:
  ```
  curl -s -X POST "<위 웹훅 URL>" -H "Content-Type: application/json" \
    -d '{"text":"⚠️ Ticket Reporter 모니터: Zendesk 세션 만료 — 로그인 필요\n로그인 페이지: <뷰 URL>\n로그인 후 다음 tick에서 자동으로 재개됩니다."}'
  ```
  같은 로그아웃 상태가 연속되는 동안은 매 틱마다 다시 보내지 않고 **틱 요약에만 "여전히 로그인
  필요"로 남긴다** — 로그인 알림은 로그아웃을 새로 감지했을 때(직전 틱은 로그인 상태였는데
  이번 틱에 로그인 화면이 뜬 경우) 한 번만 웹훅으로 보낸다. 스팸 방지용.
- 뷰 로딩/스크레이프가 2~3회 실패하면 중단하고 사용자에게 알린다 (무한 재시도 금지).
- Zendesk는 SPA다 — 뷰 간 이동은 `navigate`로 전체 URL을 다시 연다.

## SIREN check — 결함 패턴 조기경보 (사용자 지시 2026-09-21)

**목적**: 방금 보낸 티켓과 "같은 결함 + 같은 제품" 조합이 이미 (다른 Zendesk 티켓들 +
아마존 배드리뷰들 합쳐서) 3건 이상이면, 신제품 불량일 가능성이 있으니 리더에게
**해당 티켓 리포트의 Chat 스레드에 답장(reply)** 으로 알린다. "SIREN"이라고 부른다.

### 트래킹 대상 결함 — allowlist (사용자 지시 2026-09-21, /revision 피드백, HARD RULE)
**결함 태그를 유도한 뒤, 그 맨 텍스트(예: `_case__황변` → `황변`)가 `siren.py`의
`ALLOWED_DEFECT_TERMS`(약 75개 제조 결함성 용어 — 게이트홀, TPU늘어남, 디자인,
자석들뜸/탈락, 충전호환불가, 부착어려움, 버블, 힌지파손, 코팅벗겨짐 등 전체 목록은
`siren.py` 참고)에 있을 때만 카운트를 시도한다. 목록에 없으면 (예: `황변`,
`동봉제품상이함`, `배송상태불만`, `오배송`, `미배송`, `중고품배송`, `파손된상품수령`,
`기타사항`) 시도조차 하지 않고 `siren.py check --skip-reason "not in allowlist"` 로
스킵만 기록한다 — 조기 유출/배송 사고성 클레임은 신제품 불량 신호가 아니므로 SIREN
대상이 아니다.** (2026-09-29부터 `2. Delivery` 카테고리도 기본 리포트 대상에 포함되지만,
`배송상태불만`·`파손된상품수령`·`오배송`·`미배송`·`중고품배송` 등 배송성 결함 태그는
allowlist에 없으므로 SIREN 카운트 자체를 시도하지 않는다 — 구조적으로 이미 걸러짐.)
iPhone 17/18 Series 전 품목의 호환성 문의도 트래킹 제외 대상이지만,
호환 문의는 `6. Product Inquiry`라 이 체크에 도달하지 않으므로 구조적으로 이미 걸러진다
(별도 코드 불필요).
`siren.py`가 이 allowlist 체크를 자체적으로도 강제한다(방어적 이중 체크) — 브라우저
단계에서 결함 태그를 잘못 넘겨도 `siren.py`가 걸러낸다.
**주의: `황변`은 (2026-09-21 첫 라이브 SIREN이 실제로 발동했던 사례 — 티켓 #1000162927,
Galaxy S26 Ultra Hybrid MagFit) 이 규칙이 생기기 전에 보내진 것으로, 이 규칙 시행 후에는
다시 발생하지 않는다.**

### 데이터 소스
- **Zendesk**: 방금 처리한 티켓 자신 포함, 같은 결함 태그 + 같은 기기(Device) 태그 +
  같은 제품명(Product Name) 태그를 가진 모든 티켓을 Zendesk Search API로 라이브 검색
  (상태·담당자·기간 무관 — 사용자가 명시적으로 "라이브 검색" 방식을 선택함, 2026-09-21).
- **배드리뷰**: 스프레드시트 `1aYxZRm7pf5Egx6fIoAGpGg8CWzHaZ_zsBRKsvh9U1iU`의
  `신제품 라인업` 탭(A=ASIN, B=SKU, C=기종명, D=모델명)으로 티켓의 Device/Product Name을
  ASIN/SKU 집합으로 변환한 뒤, `1-3점` 탭(A=ASIN, J=Image URL, N=인입사유(tag), P=SKU,
  Q=기종명, R=모델명)에서 그 ASIN/SKU와 일치하고 인입사유(tag)가 결함의 "맨 텍스트"와
  같은 행을 센다. **모델명 텍스트는 두 시트 간에 살짝 다를 수 있어 매칭에 안 쓴다 —
  반드시 ASIN/SKU로 조인한다** (사용자 지시).
- **범위 제한 — HARD RULE (사용자 지시 2026-09-21, 확정 방침 변경 전까지 유효):**
  **SIREN은 `신제품 라인업` 탭에 실제로 등록된 제품에만 적용한다.** 티켓의 Device+Product
  Name이 `신제품 라인업`에 매칭 행이 하나도 없으면 — Zendesk 카운트가 아무리 높아도 —
  **SIREN 체크 자체를 실행하지 않고 스킵만 기록한다** (Zendesk-only로 대체 판단하지
  않음 — 2026-09-21 최초 방침에서 바뀐 부분). 현재 이 탭은 iPhone 18 Series 신제품만
  등록되어 있으므로, 사실상 SIREN은 지금 iPhone 18 Series에만 동작한다. 다른 제품군
  (Galaxy S26, Pixel Watch 등)은 이 탭에 행이 추가되기 전까지는 SIREN 알림 대상이 아니다.
- **누적 범위**: 기간 제한 없음(전체 기간 라이브 카운트, 사용자 지시 — "느리게 쌓이는
  패턴도 놓치지 않기 위해"). 오래된 매칭도 그대로 포함된다.

### 태그 유도 (Zendesk 검색 전 준비)
Zendesk 커스텀 필드 값 대신 **티켓 자신의 tags 배열**을 쓴다 — 필드ID를 몰라도 되고,
실측으로 확인된 규칙이 매우 안정적이다 (2026-09-21 검증). **주의: `(Type)` 부분을
그대로 소문자화해 접두어로 쓰면 안 된다** — 예: 필드 표시값 `(SP)_레인보우현상`의
실제 태그는 `_sp__레인보우현상`이 아니라 `_steinheil__레인보우현상`이다(SP=스크린
프로텍터 카테고리의 내부 코드네임이 "steinheil"). 그래서 결함 태그는 접두어를
추측하지 않고 **접미사(Suffix)만으로 정규식 매칭**한다:
- **결함 태그**: `1차 Defect Reason or Inquiries` 필드 표시값 `(Type)_Suffix`에서
  Suffix만 취해 tags 배열에서 `^_[^_]+__Suffix$` 패턴에 맞는 태그를 찾는다(접두어는
  무엇이든 허용). 예: Suffix `황변` → 태그 `_case__황변` 매칭, Suffix `레인보우현상` →
  태그 `_steinheil__레인보우현상` 매칭.
- **기기 태그**: `Device` 필드 값을 tags 배열의 각 태그와 "영숫자+한글만 남기고
  소문자화" 한 뒤 정확히 일치하는 태그를 찾는다(문자 형태가 달라도 — 예:
  `Google Pixel Watch 4 (45mm)` ↔ 태그 `google_pixel_watch_4__45mm_` — 정규화 비교로
  안정적으로 잡힌다).
- **제품 태그**: 먼저 `Product Name` 필드 값으로 위와 같은 정규화-정확일치를 시도한다.
  실패하면(예: 필드 `SP_Glas.tR EZ Fit Slim` vs 실제 태그
  `steinheil_ez_fit_glas.tr_slim` — 카테고리 접두어가 다르고 토큰 순서도 다름) **토큰
  포함 매칭으로 폴백**한다: 필드 값을 토큰화(영숫자/한글 외 문자로 분리)하고, 맨 앞
  토큰(카테고리 접두어로 추정)을 제외한 나머지 토큰이 전부 부분 문자열로 포함되는
  태그를 찾는다(후보가 여럿이면 가장 짧은 태그 채택).
- 셋 중 하나라도 못 찾으면 **SIREN 카운트를 시도하지 않고** `siren.py check --skip-reason
  "..."` 로 스킵만 기록한다 (억지로 근사 매칭하지 않음 — 오탐 방지).

Zendesk 인증 세션이 필요하므로 이 단계는 브라우저(claude-in-chrome, 이미 로그인된 탭)에서
`javascript_tool`로 실행한다 (`siren.py`는 Sheets/Chat만 다루고 Zendesk API는 모른다):

```js
async function siren(ticketId, fieldDisplay, deviceValue, productValue) {
  const r = await fetch(`/api/v2/tickets/${ticketId}.json`, {credentials:'include'});
  const j = (await r.json()).ticket;
  const tags = j.tags;
  function norm(s){ return s.toLowerCase().replace(/[^a-z0-9가-힣]/g,''); }
  function findTagExact(value){ const nv = norm(value); return tags.find(t => norm(t) === nv) || null; }
  function tokenize(s){ return s.toLowerCase().split(/[^a-z0-9가-힣]+/).filter(t=>t.length>0); }
  function findTagFuzzy(value){
    const toks = tokenize(value);
    const variants = [toks, toks.slice(1)];  // also try dropping the leading category prefix
    for (const v of variants){
      if (v.length===0) continue;
      let matches = tags.filter(t => { const tt=t.toLowerCase(); return v.every(tok=>tt.includes(tok)); });
      if (matches.length>=1){ matches.sort((a,b)=>a.length-b.length); return matches[0]; }
    }
    return null;
  }
  function findDefectTagBySuffix(suffix){
    const re = new RegExp('^_[^_]+__' + suffix.replace(/[.*+?^${}()|[\]\\]/g,'\\$&') + '$');
    return tags.find(t => re.test(t)) || null;
  }
  const m = fieldDisplay.match(/^\(([^)]+)\)_(.+)$/);
  let defect_tag = m ? findDefectTagBySuffix(m[2]) : null;
  const device_tag = findTagExact(deviceValue) || findTagFuzzy(deviceValue);
  const product_tag = findTagExact(productValue) || findTagFuzzy(productValue);
  let zendesk_count = null, zendesk_ids = [];
  if (defect_tag && device_tag && product_tag) {
    const q = `type:ticket tags:${device_tag},${product_tag},${defect_tag}`;
    const sr = await fetch(`/api/v2/search.json?query=${encodeURIComponent(q)}`, {credentials:'include'});
    const sj = await sr.json();
    zendesk_count = sj.count;
    zendesk_ids = (sj.results||[]).map(t=>t.id);
  }
  return {defect_tag, device_tag, product_tag, zendesk_count, zendesk_ids};
}
```

**`신제품 라인업` 조회도 같은 이유로 폴백이 필요하다** (2026-09-21 확인: 티켓 Product
Name `SP_Glas.tR EZ Fit Slim` vs 시트 모델명 `Glas.tR EZ Fit`) — `siren.py`의
`lookup_asin_sku_set()`이 이미 처리한다: 기종명+모델명 정확 일치를 먼저 시도하고,
매칭이 없으면 정규화한 문자열 간 부분 포함(어느 방향이든)으로 재시도한다. 이 폴백
덕분에 실제로는 `신제품 라인업`에 있는 제품을 "등록 안 됨"으로 잘못 스킵하는 일을
피한다 — 위 "범위 제한" 스킵을 적용하기 전에 반드시 이 폴백까지 거친 결과인지
확인한다.
**중요(Zendesk Search API 문법, 2026-09-21 실측)**: 여러 태그를 AND로 조합하려면 반드시
`tags:a,b,c` 처럼 **콤마로 이어 붙인 하나의 `tags:` 필드**를 써야 한다. `tags:a tags:b`
처럼 필드를 반복하면 **OR**로 동작한다(Zendesk Search API의 알려진 동작 — 실측으로
확인: 반복형은 개별 카운트보다 큰 합집합 결과가 나왔음). 절대 반복형을 쓰지 않는다.

### 카운트·트리거·로깅 — `siren.py`
위 JS 결과(defect_tag, device_tag, product_tag, zendesk_count, zendesk_ids)와 티켓의
Device/Product Name 값을 그대로 넘겨 실행한다:

```
python3 ~/.claude/skills/ticket-reporter/siren.py check --ticket-id <번호> \
  --defect-tag "<예: _case__황변>" \
  --device "<Device 필드 값>" --device-tag <위 결과> \
  --product-name "<Product Name 필드 값>" --product-tag <위 결과> \
  --zendesk-count <위 결과> --zendesk-ids '<위 결과 JSON 배열>'
```

`siren.py`가 하는 일(모두 자동):
1. `신제품 라인업`에서 Device+Product Name 일치 행들의 ASIN/SKU 집합을 구한다(색상별로
   여러 개일 수 있음 — 전부 모은다).
2. `1-3점`에서 그 ASIN/SKU 집합과 일치 + 인입사유(tag)가 결함 맨 텍스트(`_case__황변` →
   `황변`)와 같은 행을 센다.
3. `total = zendesk_count + bad_review_count`. **`total >= 3`이면 SIREN 발동.**
4. 매 실행(발동 여부 무관)을 다음 두 곳에 **항상** 기록한다:
   - 로컬 `state/siren_log.json` (전체 상세 — 매칭 티켓ID/리뷰ID 포함)
   - 티켓 리포터 자체 큐 스프레드시트(`1GUU2CLa60XSGWHI6yZ6Jkx4nrzcGgBJnuxwQAZktH7M`)의
     `SIREN_Log` 탭 (한 행 요약)
5. **재알림 방지**: 같은 (defect_tag, product_tag) 조합이 과거에 이미 발동(triggered)한
   적이 있으면, 이번에도 조건을 넘어도 **다시 알리지 않고 로그만 남긴다** (매 신규 티켓마다
   같은 스레드가 도배되는 것 방지). 그 조합이 **처음** 3건 이상이 된 그 티켓에서만 실제
   알림을 보낸다. (재알림 기준을 바꾸고 싶으면 — 예: "N건 더 늘 때마다 재알림" — 사용자
   지시 필요, 현재는 클러스터당 1회.)
6. 알림 발동 시, 그 티켓의 리포트가 걸린 Chat 스레드(큐 시트 `TicketQueue` 탭에서 조회)에
   **답장으로**(새 메시지 아님) 다음을 담아 보낸다:
   - 결함·기기·제품명, 누적 건수(Zendesk/배드리뷰 분리 표기)
   - 매칭 Zendesk 티켓 링크(최대 10개 + "외 N건")
   - 매칭 배드리뷰 이미지(Image URL 컬럼, 최대 10장, grid 위젯)
   스레드를 못 찾으면(TicketQueue에 기록 없음) 알림 전송 실패로 로그에 남기고 조용히 넘어간다
   (원본 리포트 전송 자체는 이미 성공했으므로 별도 사용자 알림 불필요 — 틱 요약에만 언급).

### 대상 판정 및 dedup
A열(Status)을 trim한 값이 정확히 `Esc T2`인 행만 대상 (시트에 `"Esc T2 "`처럼 trailing
space가 붙어 있는 경우가 있어 반드시 trim 후 비교). 그 외(`Solved` 등)는 무시. Zendesk
소스와 달리 Category 게이트는 없음 — TCT가 이미 `Esc T2`로 에스컬레이션한 것 자체가 Tier
2(GCX) 검토 필요 신호이므로 모든 `Esc T2` 행이 대상.

`state/processed.json`에 두 구조를 함께 쓴다:
- `processed_tct_log`: 지금까지 한 번이라도 전송한 티켓 키 목록(`"<lazada|shopee>_<Ticket ID>"`,
  B열이 비어 있으면 `"<lazada|shopee>_ord<Order ID>"`) — 참고용 전체 이력.
- `tct_log_state`: `{ "<키>": { "cycled_through_t1": true|false } }` — **재인입 판단용
  (사용자 지시 2026-09-18):** "한 번 보낸 티켓은, A열이 `Esc T1`로 바뀌었다가 다시
  `Esc T2`로 돌아오지 않는 한 다시 보내지 않는다." 매 스캔마다 두 탭의 A~B열 전체를 읽어
  `tct_log_state`에 이미 있는 모든 키의 **현재 Status**를 확인하고:
  - 현재 Status(trim)가 `Esc T1`이면(사람이 `/voucher` 답장을 보내 `updateTctLogRow_`가
    A열을 `Esc T1  `로 바꾼 상태) → 해당 키의 `cycled_through_t1`을 `true`로 기록한다
    (아직 리포트를 다시 보내지 않음 — 상태 변화만 기록).
  - 현재 Status(trim)가 `Esc T2`이고 `cycled_through_t1`이 `true`였다면 → **TCT가 재에스컬레이션한
    것이므로 신규 건처럼 리포트를 다시 생성·전송**하고, 전송 후 `cycled_through_t1`을
    `false`로 리셋한다 (다음 사이클을 위해).
  - 현재 Status(trim)가 `Esc T2`이고 `cycled_through_t1`이 `false`(또는 키가 아직 없음)면
    → 기존과 동일하게 스킵(이미 보낸 최초 에스컬레이션, 아직 사람 답장 전).
  - 그 외 상태(`Solved` 등)는 `cycled_through_t1`을 건드리지 않는다 — 오직 `Esc T1`
    (advice 완료) → `Esc T2`(재에스컬레이션) 왕복만 재전송 트리거.
  신규 티켓(아직 `tct_log_state`에 없음)은 기존과 동일하게 그대로 전송 후
  `{"cycled_through_t1": false}`로 등록.

### 첨부 처리 (Google Drive 폴더 또는 개별 파일)
1. Sheets API `spreadsheets().get(spreadsheetId=SSID, ranges=["'<탭>'!R<행번호>"],
   includeGridData=True, fields='sheets.data.rowData.values(hyperlink)')`로 R열 셀의
   `hyperlink`를 뽑는다 — `values().get()`의 일반 텍스트 값("Image")이 아니라 이
   hyperlink 필드가 실제 링크다. **두 형태가 모두 나올 수 있다 (2026-09-18 확인):**
   - 폴더 링크: `.../drive/folders/<folderId>?usp=...`
   - 개별 파일 링크: `.../drive/file/d/<fileId>/view?usp=...` (Lazada log 행은 보통
     폴더, Shopee log 행은 파일 하나만 걸리는 경우가 있었음 — 소스탭으로 어느 형태인지
     단정하지 말고 URL 패턴으로 분기할 것)
2. URL 패턴으로 분기:
   - `/folders/([a-zA-Z0-9_-]+)` 매치 → 폴더로 취급, 3번으로.
   - `/file/d/([a-zA-Z0-9_-]+)` 매치 → 파일 하나만 있는 것으로 취급, Drive API
     `files().get(fileId=<fileId>, fields='id,name,mimeType,webContentLink,thumbnailLink')`
     로 그 파일 메타데이터를 바로 가져와 4번으로 (폴더 목록 조회 생략).
3. (폴더인 경우) Drive API `files().list(q=f"'{folderId}' in parents",
   fields='files(id,name,mimeType,webContentLink,thumbnailLink)')`로 폴더 안 실제 파일
   목록을 가져온다.
4. `mimeType`이 `image/*`면 **`--image`에는 `thumbnailLink`를 크기만 키워서 쓴다** —
   끝의 `=sNNN`을 `=s1600`으로 치환(정규식 `re.sub(r'=s\d+$', '=s1600', thumbnailLink)`).
   `webContentLink`(`https://drive.google.com/uc?id=...&export=download`)는 **카드에
   이미지가 실제로 렌더링되지 않는다** — 303 리다이렉트를 거쳐야 실제 파일이 나오는데
   Chat 카드의 image/grid 위젯은 이 리다이렉트를 따라가지 않고 링크 텍스트만 표시함을
   확인함(사용자 리포트, 2026-09-18). `thumbnailLink`(`lh3.googleusercontent.com/...`)는
   리다이렉트 없이 200 + 실제 이미지 바이트를 바로 반환해 image/grid 위젯에 정상 렌더링됨.
   video/*, application/pdf 등 이미지가 아닌 파일은 그대로 `--attach "<name>|<webContentLink>"`
   로 넘긴다 (링크 클릭 시 브라우저가 리다이렉트를 알아서 따라가므로 문제 없음). 이 시트의
   첨부 폴더들은 "anyone with link" 권한으로 공유돼 있어 두 링크 형태 모두 인증 없이
   접근 가능함을 확인함, 2026-09-18.
5. 폴더가 비어있거나 하이퍼링크가 없으면 첨부 없이 리포트만 전송한다.

### Chat 스레드 답장 → 시트 반영 (TicketReporterCard/Code.gs, 사용자 지시 2026-09-18)
Zendesk 소스와 달리 이 소스는 **내부 노트를 안 쓴다.** 팀원이 리포트 스레드에
`@Ticket Reporter <메모>`로 답장하면 (`postThreadReplyAsNote_`가 아니라) `updateTctLogRow_`가
처리한다 — ticket id가 순수 숫자가 아니면(`/^\d+$/` 불일치) 이 경로로 분기.
- `/revision`·`처리 요청 사항`·`[GCX <컨펌>]` 래핑 **전혀 없음** — 답장 메모 원문을
  (있다면 `/voucher N%` 토큰만 제거하고) 그대로 U열(Advice/Internal Memo)에 쓴다.
- 답장에 `/voucher 100|50|10[%]`가 있으면 T열(Voucher)에 정확히
  `Provide 100% voucher` / `Provide 50% voucher` / `Provide 10% voucher` 로 쓴다 (시트의
  strict 드롭다운 문자열과 **완전히 동일**해야 함 — 다른 숫자면 T열은 건드리지 않음).
  없으면 T열은 그대로 둔다.
  예: `@Ticket Reporter /voucher 100% let's give him a exceptional voucher since we can
  see scratch on the image` → T=`Provide 100% voucher`, U=`let's give him a exceptional
  voucher since we can see scratch on the image`.
- 항상 V열(GCX STATUS✅) = `Advice given`, A열(Status) = `Esc T1  ` **(주의: 뒤에 공백
  2칸 — 시트 드롭다운 값 자체에 있는 오타성 공백이며, 조건부 서식이 이 문자열과 정확히
  일치해야 색이 입혀지므로 절대 trim하지 않는다. 2026-09-18 두 탭 모두에서 확인.)**
- 컬럼 상수는 `Config.gs`의 `TCT_LOG_SHEET_ID`/`TCT_LOG_TABS`/`TCT_LOG_COL`에 정의.

## Notes / gotchas
- Webhook 메시지는 편집·삭제 불가. 잘못 보내면 사용자가 Chat에서 수동 삭제.
- 카드 본문 HTML은 Google Chat이 지원하는 태그만 해석: `<b> <i> <u> <s>
  <font color="#hex"> <a href> <br>`. `<ul>/<li>`·마크다운(`*`,`**`)은 안 됨 → 숫자/`+`
  기호 + `<br>` 로 목록을 만든다.
- 앱카드 위 별도 `text` 줄은 없다 (`send.py`가 카드만 보냄).
- 줄 간격: 붙는 필드는 `<br>` 하나, 섹션 헤더·리스트 항목 사이만 `<br><br>` 하나.
  빈 줄 2개 이상 금지 ("출력 렌더링" 참고).
- `링크:` 줄과 `#티켓번호`는 모두 `<a href="…/agent/tickets/N">`.
- `textParagraph`는 ~4096자 제한. `send.py`가 `<br>` 기준으로 자동 분할하지만 본문은
  보통 2KB 내외라 문제 없음.
- **파일 내 실제 줄바꿈(`\n`)은 `send.py`가 공백 1개로 접는다** — Google Chat은
  `\n`을 줄바꿈으로 렌더하므로 `<br>` 뒤에 파일 개행이 있으면 두 줄씩 벌어진다.
  그래서 간격은 **오직 `<br>`(줄바꿈)·`<br><br>`(빈 줄 1개)** 로만 준다. `body.html`을
  한 줄로 쓰든 여러 줄로 쓰든 상관없고, 각 논리 줄 끝에 `<br>`를 반드시 넣는다.
- 첨부 이미지 위젯이 안 뜨는 경우가 있어(만료/권한) `send.py`가 링크 목록도 항상 같이 넣는다.
- `[TCK 예상 답변]`을 못 찾으면 지어내지 말고 `확인 불가`라고 쓴다.
- 구매 경과 기간은 `구매일자` → 오늘(KST) 기준 개월(일) 둘 다 표기. `[비고]`의 "+ 구매 NN개월
  경과" 줄은 2개월 초과 시 빨강; `[Ticket Info.]`의 `구매일자:` 날짜 자체는 3개월 이상 경과 시
  별도로 빨강 (두 기준 다르니 혼동 금지 — 사용자 지시 2026-09-16).
- `[GCX AI 예상답변]`의 `동일`은 **항상 괄호 근거 필수** (HARD RULE 8).
